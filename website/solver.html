24 点求解器Twenty-Four Solver · Algorithm Deep Dive

精确，是速度的前提 · Exact First, Fast Second

这是 24点大作战 背后的精确求解引擎：用 Long 精确分数 做算术，用 成对合并 DFS 做搜索，用 uint64 状态键 做剪枝，用 1820 组合查找表 做常量化。没有浮点数、没有热路径对象分配，也没有一行 java.* 依赖 —— 可直接放进 Compose Multiplatform 的 commonMain。

Step 0 · Why Exact

为什么第一行代码就要禁掉浮点

24 点最经典的牌面 [3,3,8,8]，唯一解法必经分数 8/3 与 1/3。用双精度浮点算，结果会「看起来等于 24」——下面的演示在你的浏览器里现场运行。

IEEE 754 双精度（页面现场计算）

求解器：Long 精确分数（n/d 互质）

所以 PRD 第一条硬性规定就是：禁用 Float / Double，禁止 epsilon 比较。求解器的每一次相等判断都是整数叉乘 n·targetD == targetN·d，每一次加减乘除都有溢出检测（mulExact / addExact），溢出则无缝切换到 BigNum 兜底引擎（见下文 §5）。
Step 1 · Core Search

核心算法：成对合并 DFS

任意时刻，局面就是一组分数。每一步任选两张合并成一个新值，局面从 4 张缩到 3 张、2 张、1 张 —— 递归深度恒等于 3。

0a + b 1a − b 2b − a 3a × b 4a ÷ b 5b ÷ a

每对组合，固定 6 个候选

候选按 + a−b b−a × a÷b b÷a 的固定顺序生成，值相同的候选就地去重（如 2+2 与 2×2 只保留前者）。固定顺序带来一个工程上奢侈的性质：完全确定性 —— 相同输入永远得到逐字节相同的输出。

搜索空间有多大？

不剪枝的合并序列共 36 × 18 × 6 = 3888 条；加上状态去重后，单局真正展开的不同状态上界约 684（源码注释值）。递归深度 ≤ 3、候选缓冲 ≤ 6 —— 一切都在启动前分配好。

真实源码（节选）

if (count == 1) { // n·targetD == targetN·d 整数叉乘 if (mulExact(intern.n(ids[0]), targetD) == mulExact(targetN, intern.d(ids[0]))) { …; return true } return false } for (i in 0 until count-1) for (j in i+1 until count) { val cc = genCandidates(ids[i], ids[j], depth) for (k in 0 until cc) { merge(i, j, k) // 原地合并 if (visited.add(encodeState(count-1)) && dfs(count-1, depth+1)) return true restore(i, j, …) // O(1) 撤销 } }
Step 2 · Hot Path

零分配热路径：9 个字节存一条解

整个搜索过程不创建任何对象、不拼任何字符串 —— 靠三件套：互质 Long 分数、原地 compact/restore、3 字节步记录。

互质 Long 分数

每个中间值是规范化的 (分子, 分母)：符号归分子、分母恒正、gcd 约分。相等判断只做一次叉乘。App 里的分数卡牌显示（分子/分母上下结构）直接来自这个表示。

83 → 3 − 83 → 13

原地 compact / restore

合并结果写入槽 i，活动区末尾元素换到槽 j，长度减一；回溯时一次交换精确还原。没有数组拷贝，没有链表。

3S0 3S1 8S2 8S3 → 8/3S0 3S1 8S2

3 步 × 3 字节 = 9 字节

命中解之前，路径只是 steps: ByteArray(9) 里的 9 个字节；字符串与表达式树只在命中之后才构建。[3,3,8,8] 的解路径真实编码如下：

第 1 步 i=0 · j=2 · op=5（b÷a → 8/3）
00010101
21 = (0<<6)|(2<<3)|5
第 2 步 i=0 · j=1 · op=2（b−a → 1/3）
00001010
10 = (0<<6)|(1<<3)|2
第 3 步 i=0 · j=1 · op=5（b÷a → 24）
00001101
13 = (0<<6)|(1<<3)|5
除零连分支都不需要：a÷b 生成的新分母是 dA·nB，b 为 0 时分母自然为 0，被统一的「分母为零即丢弃候选」规则过滤 —— 同一条规则同时兜住了真正的除零 bug。
Step 3 · Memoization

记忆化：把分数变 ID，把状态变一个 Long

剪枝的关键是「认出以前见过的局面」。为此求解器给每个分数发一个 uint16 身份证，再把整个局面压进 64 个比特。

InternTable：分数 → uint16 ID

开放寻址哈希表（8192 槽、线性探测、fmix64 混淆），把每个规范化分数映射成从 1 编号的 ID。相同数值共享同一 ID —— 2/4 与 1/2 是同一个 #7。ID 每次 solve 重建，绝不跨局复用。

2/4输入 → 1/2约分 → #7intern ＋ 1/2再次出现 → #7命中

encodeState：局面 → uint64

搜索会反复走进「数值相同、顺序不同」的局面。把 4 个 ID 按数值大小排序（叉乘比较），再按 4×16bit 打包成一个 Long —— 规范键唯一，VisitedSet（2048 槽、负载 < 0.5）一次 add 就能跳过整棵重复子树。

#0716 bit #0B16 bit #2116 bit #3416 bit
按数值升序打包 → 0x0022_0015_000B_0007（示意）
剪枝不改变可解性：被跳过的只是「与已探索局面等价」的分支。这也解释了为什么多解枚举模式按表达式字符串去重后，返回的解全部有效、两两不同，但不承诺穷尽所有书写形式 —— 求解器对此如实声明，不做过度承诺。
Step 4 · Fallback

BigNum 兜底：溢出时无缝切换的大整数

标准路径的中间值恒在 Long 范围内；一旦自定义目标或超范围输入可能越界，mulExact 抛出 OverflowSignal，AUTO 模式自动换装同一套 DFS 的大整数引擎重跑。

什么时候触发？

三种情况：输入超出 1..13（含 0 / 负数 / 大数）；标准路径抛出溢出信号；或调用方显式指定 FALLBACK 模式。切换对调用方完全透明，结果一致（1820 组合上做过一致性断言）。

符号 + 幅值，32-bit limb

纯 Kotlin 手写：IntArray 小端 32 位 limb + 符号位。乘法是 O(n·m) 组合乘法；为了不依赖任何 128 位类型，64/32 除法被拆成 4 个 16 位块处理。中间值上界约 2^248（8 个 limb），绰绰有余。

// 热路径之外的最后防线 limbs: [L0, L1, L2, …] // 2³² 进制小端 negative: false // 0 恒为正

Knuth Algorithm D

大数除法按 TAOCP 4.3.1 实现：先做位移归一化，再用 16 位分块估商 q̂，按 D3 修正、D4 乘减、必要时 D6 加回。唯一用到 java.math.BigInteger 的地方是测试——3 万组随机数对照，逐位一致。

Step 5 · The Lookup Table

1820 张牌面，答案全部已知

1..13 里可重复地抽 4 张，无序组合恰好是 C(16,4) = 1820。求解器在首次使用时把它们全部解一遍，做成惰性查找表 —— 下面的网格正用同一算法在你的浏览器里重建它。

4 bit 一张牌

键 = 升序四张牌，每张塞进一个 nibble，拼成 uint16 → IntArray(65536) 直接索引；条目区存 3 个 15bit 打包步骤，共约 28 KiB。

惰性构建 · 严格准入

首次满足「target=24、全运算符、单解、1..13」的求解触发全量构建；其余请求照走通用 DFS，两条路永远都在。

禁止手工维护

每条入表解法都由一个独立的 BigNum 求值器复验（不与 DFS 共享分数代码），验证失败直接 check 失败 —— 表永远可信。

Step 6 · In the Game

在游戏里：4 → 3 → 2 的提示阶梯

引擎没有「三数版算法」「两数版算法」—— 同一个 DFS 换个输入数量而已。游戏因此能跟着剩余牌数实时给精确提示，包括分数局面。

最后一步提示 · ≤6 候选 · O(1)

简单难度：杜绝死局

合并前先 solveThree 预校验「合并后剩余三张仍可解」，否则拒绝这一步 —— 新手永远不会把自己玩死。

中等+：死步可撤销

合并一旦把局面带进死路（剩余牌无解），立即弹窗提示并开放撤销 —— 判定同样来自 solveThree / solveTwo。

无解按钮 · 超难发牌

「无解」判定 = 开局 solve().status，答错扣分防试探；超难难度还要再过「窄解过滤器」—— 解法唯一或近唯一的牌面才配出现。
